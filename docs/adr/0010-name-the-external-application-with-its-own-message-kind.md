# Name the External Application with its own message kind

A Computer reaches the External Application with `external_call`, a message kind of its own, rather than with a `service_request` carrying a widened destination. A `service_request` destination is `{customer_network_id, computer_id? | address?}` — it is scoped to a Customer Network, and the External Application is not one. Widening it would put a form in the destination that no router, ISP, or Central Server may ever route on, and would add a special case to every destination check in CraftNet to make sure none of them tried. The kind is the destination instead: there is nothing to scope, so nothing is scoped, and the roles that must refuse it — a router asked to serve one inbound, an ISP asked to carry one downward — refuse it by kind rather than by inspecting a field.

The answer comes back as an ordinary `service_response`. The reply path is genuinely identical: the source Customer Router opened a NAT Flow, the flow identifier travels back, and the router finds the one Computer that asked among however many hold the same RFC 1918 address. Giving external replies their own kind would have duplicated that rule in the Computer, the router, and the ISP, and a second copy of a rule is a second place for it to drift.

The credential an operation may present is one rule, applied at both ends of the path: a Computer refuses its own mistake before the call leaves, and the External Application refuses it again on arrival. `device.register` presents a `registration_nonce` and nothing else, because the authenticated ancestry every hop derived is the attestation; `token.issue` and `device.rotate` present the Device Credential; every other operation presents an Access Token.

This settles the question [Milestone 6 deliberately deferred](../implementation/milestone-6.md#deliberately-deferred). The wire version stays `1`: nothing has been released, so there is no deployed peer to keep compatible, and settling the question now is what the release gate was waiting for.
