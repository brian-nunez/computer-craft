# CraftNet v0.1.0 — release notes

**Draft.** These notes describe what v0.1.0 is. It is not tagged yet: see
[the acceptance report](../implementation/acceptance/report-v0.1.0.md) for what
still has to happen first.

CraftNet is an in-world networking simulation for CC:Tweaked. It gives a
Minecraft world a Central Server, ISPs, Customer Routers, and Computers, with
real addressing, real name resolution, real routing, real NAT, and a controlled
way out to an application outside the game.

## What is in v0.1.0

**Seven Lua packages**, installed with `ccpm`:

| Package | What it is |
|---|---|
| `craftnet-protocol` | The v1 wire: canonical JSON, SHA-256 and HMAC in pure Lua, key derivation, strict schemas, the session handshake, counters and replay rejection, framing, correlation, size limits, timeouts |
| `craftnet-core` | Pure role state transitions. No file, no modem, no timer, no clock — time arrives as an argument |
| `craftnet-runtime` | The orchestration around those transitions: snapshots, secrets, links, enrollment, connectivity, screens, and the CraftOS adapters |
| `craftnet-central` | The Central Server |
| `craftnet-isp` | An ISP |
| `craftnet-router` | A Customer Router |
| `craftnet-computer` | A Computer |

**One Go binary**, `craftnetd`: the Gateway a Central Server connects to, the
embedded Operator dashboard, and the dashboard API, on one origin and out of one
SQLite file. CGo-free, so it is one file with nothing to install beside it.

### What it does

- **Addressing that overlaps on purpose.** Every Customer Network may use the
  same RFC 1918 pool. `alex-pc` on Home and `harvester` on Farm both hold
  `192.168.1.20`, and nothing anywhere is ambiguous about it.
- **Hierarchical names.** `harvester`, `harvester.farm`, and
  `harvester.farm.acme.craft` all resolve, widening a label at a time.
- **Exact routes.** One entry per Customer Network. No routing protocol and no
  prefix matching: a range here organises allocation, not delivery.
- **Paired NAT Flows.** A cross-network reply retraces the path its request
  took, matched by flow identity rather than by address.
- **Closed by default.** A Computer is reachable inside its own network as soon
  as it joins, and from anywhere else only when an Operator publishes a service.
- **One-time enrollment.** Sixteen characters in four groups, carried from one
  screen to the next. A parent stores no token, only which ones it has spent.
- **Durable everything that matters.** Identities, addresses, hostnames, routes,
  statuses, and credentials survive a restart. Sessions, counters, and NAT Flows
  do not, and are meant not to.
- **An Operator dashboard.** A topology canvas as the primary view, with linked
  traffic and incident views, credential *status* without credential *values*,
  and confirmed enable/disable of a Customer Network with audit history.
- **A named-operation allowlist** outside the game. `device.register`,
  `token.issue`, `echo`, `time.now`, and `test.identity`. Adding one is a
  handler plus a policy at the composition root — never a new route, a new
  session, or a proxy to an arbitrary URL.

## The tested scale

These are the numbers this release has actually been run at. **They are not
architectural maxima, and nothing here should be read as a capacity claim.**

| | Tested at |
|---|---|
| Topology entities | 1,685 — 4 ISPs, 20 Customer Routers each, 20 Computers each |
| Mixed operations in one run | 10,000, seeded and deterministic |
| Reference load | 1,000 mixed local, cross-network, and external requests |
| Outstanding requests per relationship | 64; the 65th is refused with `busy` |
| Gateway operations in flight | 256 |
| Traffic batch | 100 events, 128 KiB |
| Raw modem frame | 16 KiB |
| Topology snapshot | 2,000 entities |
| Rolling diagnostic buffers | 100 per router and Computer, 500 per ISP, 2,000 at Central |

Every one of those bounds refuses work past it rather than queueing it. A queue
with no bound is a slower way of failing, and it fails later, larger, and
somewhere less obvious.

The scale figures come from a deterministic simulator running real state
transitions, not from a Minecraft server. What a real server does at that size
is not known, and this release does not claim to know it.

## What v1 deliberately does not have

Not oversights — decisions, each one taken to keep the model small enough to
explain:

- **No subnet masks and no prefix routing.** A Customer Network is a unit, not a
  range. The Central Server's map has one entry per network.
- **No ports and no connections.** A remote request creates a paired ephemeral
  flow and nothing else.
- **No Computer-to-Computer path.** Every request goes to the Customer Router,
  local or not.
- **No routing protocol, no multi-homing, no failover.** One route, one ISP, one
  Central Server per World.
- **No fragmentation.** A caller that exceeds a limit is told to shrink its
  payload or its batch.
- **No automatic address eviction.** An Address Binding is permanent. An
  exhausted pool is an Operator's decision to make, not something CraftNet
  quietly resolves by taking an address away from a running Computer.
- **No replay of an interrupted request.** If a call was cut off, it is gone.
  CraftNet does not decide on its own to do again what a player asked for once.
- **No proxy to arbitrary URLs.** The External Application exposes a named
  allowlist and nothing else.
- **No multi-World federation.** One World per `craftnetd` database entry, and
  Worlds do not talk to each other.
- **No downgrade path.** Database and snapshot migrations are forward-only.

## The external path, from a Computer

A Computer reaches the External Application by name:

```
craftnet call api.craft test.identity
```

`api.craft` is the one CraftNet Name that is not a Computer, and it has no
address: it is reached through a named operation and the ancestry every hop
derived, never by routing to it. On the wire it is
[`external_call`](../adr/0010-name-the-external-application-with-its-own-message-kind.md),
a message kind of its own — the Customer Router NATs it like any remote request,
the ISP carries it, and the Central Server, which holds the World's one
WebSocket, puts it on the Gateway with the ancestry stamped from the route
directory.

The first call from a Computer registers it and gets it a two-minute Access
Token. Neither is done by hand.

When `craftnetd` is not reachable, external calls give `gateway_unavailable` and
nothing else changes. The Central Server reconnects under bounded backoff, sends
a fresh topology snapshot, and resumes reporting.

## Known limitation in this release

**Traffic Events do not travel upstream in world.** A Customer Router and an ISP
record their own; only the Central Server's reach the dashboard. What Traffic
shows is therefore the Central Server's view of a World, not every role's. See
[Milestone 9](../implementation/milestone-9.md) for why that was left open
rather than improvised.

## Compatibility

| | |
|---|---|
| Minecraft | 1.21.11 |
| Mod loader | Fabric |
| CC:Tweaked | 1.117.1 |
| Lua | 5.2, as CC:Tweaked provides |
| Go | 1.27.0 |
| CraftNet wire | 1 |
| Database schema | 17 |

`craftnetd` migrates its database forward at every start. Migrations are
forward-only and safe to repeat. Downgrading is not supported; copy the database
file first if you want the option.

## Getting it

```bash
ccpm install craftnet-central     # and isp, router, computer
```

Binaries and their `SHA256SUMS` are built by
[`scripts/build-release.sh`](../../scripts/build-release.sh). Every release
binary is stamped with the version it claims to be; a binary built any other way
reports `0.1.0-dev`, so a build can never claim to be a release nobody cut.
