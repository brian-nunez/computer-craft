# The CraftNet v1 wire

This is the contract two independent implementations meet on: `craftnet-protocol`
in Lua and `external/internal/protocol` in Go. Neither one is the specification.
**[The fixture catalog](../../spec/protocol/v1/) is** — it is executable, both
languages replay it, and CI fails if they disagree. This document explains what
the catalog encodes and why, so that a reader does not have to reconstruct the
reasoning from JSON.

If prose here and a fixture disagree, the fixture is right and this document has
a bug. Say so.

The protocol version is the integer `1` and does not change within v1. An
unknown major version is refused with `unsupported_version` rather than guessed
at.

## Shape of it

Every message is a UTF-8 JSON object. Field names and message kinds are
lowercase `snake_case`.

There are four **transports**, and a kind belongs to one or more of them. A kind
offered on a transport that does not carry it is `invalid_message` — checked
before anything else about it is considered.

| Transport | Authenticated by | Kinds |
|---|---|---|
| `discovery` | nothing, by design | `discover`, `offer` |
| `handshake` | an outer proof | `enroll_open`, `enroll_challenge`, `enroll_confirm`, `enroll_accept`, `enroll_error`, `session_open`, `session_challenge`, `session_confirm` |
| `operational` | a session MAC | `ack`, `command_result`, `config_request`, `config_snapshot`, `dns_query`, `dns_result`, `error`, `external_call`, `heartbeat`, `network_status_set`, `route_register`, `route_remove`, `service_request`, `service_response`, `topology_change`, `topology_snapshot`, `traffic_batch` |
| `gateway` | WSS and the Gateway Session | `ack`, `admin_command`, `command_result`, `error`, `external_request`, `external_response`, `heartbeat`, `topology_change`, `topology_snapshot`, `traffic_batch` |

**Unknown fields are rejected**, everywhere, in every authentication and control
message. There is exactly one exception: an **External Operation payload object
is application-defined** and may carry fields this version has never seen. That
is the only place in CraftNet where a receiver tolerates what it does not
recognise, and it is deliberate — payloads belong to whoever wrote the
operation, not to the protocol.

**An optional field is omitted, never encoded as an empty substitute.** `null`,
`""`, and `0` are not ways of saying "absent"; leaving the key out is. A
fixture asserts this for `ack.result_revision`.

## Scalars

Every field is validated against one of these before dispatch.

| Rule | What passes |
|---|---|
| `id` | 1–64 chars matching `^[a-z0-9][a-z0-9_-]*$` |
| `normalized_name` | 1–32 chars, lowercase letters/digits with internal hyphens, beginning and ending with a letter or digit |
| `display_name` | 1–32 characters, otherwise unconstrained |
| `operation_name` | 1–64 chars matching `^[a-z0-9._-]+$` |
| `nonce`, `digest` | exactly 64 lowercase hex characters (32 bytes) |
| `integer` | an exact integer in `±(2^53-1)`; fractional and non-finite are invalid |
| `non_negative`, `revision`, `milliseconds` | an integer `>= 0` |
| `positive` | an integer `>= 1` |
| `channel` | an integer `0`–`65535` |
| `customer_address` | a dotted-quad string inside RFC 1918 (`10/8`, `172.16/12`, `192.168/16`) |
| `provider_address` | a dotted-quad string inside RFC 6598 (`100.64.0.0/10`) |
| `timestamp` | RFC 3339, UTC, `Z`-suffixed |
| `role` | `central` \| `isp` \| `router` \| `computer` |
| `connectivity_state` | `connecting` \| `ready` \| `degraded` \| `disconnected` \| `revoked` |
| `network_status` | `enabled` \| `disabled` |
| `direction` | `inbound` \| `outbound` \| `local` |
| `topology_change` | `added` \| `updated` \| `removed` |
| `entity_type` | `isp` \| `customer_network` \| `router` \| `computer` |
| `command_status` | `applied` \| `rejected` |

Two things follow from the numeric rule that are easy to get wrong:

- **There are no decimals on this wire.** An operation that needs one uses a
  string or a scaled integer. A fractional number is `invalid_message`, not a
  rounding decision.
- **Addresses are strings, and leading zeros are refused.** `192.168.01.1` is
  not an address.

**IDs never embed a display name or an address.** They are opaque. A reader that
parses meaning out of an ID has invented a coupling the protocol does not offer.

**Timestamps appear only on the Gateway.** In-world messages carry integer
monotonic milliseconds, for durations and observations only. Nothing about
CraftNet security depends on a Computer's wall clock, which a player can set.

## CraftNet Canonical JSON 1

Every HMAC input is CJ1. It exists so that a signature covers exactly the bytes
the peer validated — not a re-serialisation that might differ.

CJ1 encodes null, booleans, integers, strings, arrays, and objects with standard
JSON tokens, and:

- emits no insignificant whitespace
- preserves array order
- **sorts object keys by unsigned UTF-8 byte order** — not by the C locale,
  which would make canonical output depend on the host
- escapes control characters as lowercase four-digit `\u00xx`
- otherwise emits valid UTF-8

Decoding rejects everything the canonical form cannot round-trip: duplicate
keys, sparse arrays, mixed table keys, non-string object keys, fractional
numbers, values outside the exact integer range, unescaped control characters,
overlong UTF-8, surrogates, and out-of-range scalars.

**An empty array and an empty object are different values and stay different.**
In Lua a bare `{}` is ambiguous, so it resolves to an object; an empty array
must be built explicitly with `protocol.array({})`.

Golden vectors: [`spec/protocol/v1/cj1/`](../../spec/protocol/v1/cj1/).

## The three framings

### Discovery

Unauthenticated by design, and it answers nothing in detail. A failure here is
silence, because a reply on a shared channel tells a listener something.

```json
{ "v": 1, "kind": "discover", "body": { ... } }
```

### Handshake

Used before a session key exists. `proof` is an HMAC over the whole canonical
outer message under the one-time enrollment secret, LAN Password, or durable
relationship credential.

```json
{ "v": 1, "kind": "enroll_open", "request_id": "req-join-1", "body": { ... }, "proof": "<64 hex>" }
```

The proof preimage is `CJ1([1, kind, request_id, body])`.

### Operational

Every message on an established relationship.

```json
{
  "v": 1,
  "kind": "service_request",
  "relationship_id": "rel-router-farm",
  "session_id": "ses-42",
  "request_id": "req-harvester-104",
  "counter": 17,
  "body": { },
  "body_hash": "<64 hex>",
  "mac": "<64 hex>"
}
```

- `body_hash` is `SHA256(CJ1(body))`.
- The MAC preimage is `CJ1([1, kind, relationship_id, session_id, request_id, counter, body_hash])`,
  where a message with no request correlation uses the **empty string** for
  `request_id` — not a null, and not an omitted element.
- `mac` is `HMAC-SHA256(session_key, preimage)`.
- `request_id` is the only optional envelope field.

**A receiver validates in this exact order:** types and size, then relationship,
then session, then a strictly increasing counter, then the body hash, then the
MAC — and only then dispatches. The counter is committed **after** the MAC
verifies, so a forged frame cannot advance the window. On the sending side the
counter is committed only after a successful encode, so a failed encode never
burns a value.

The first operational counter of a session is `1`.

## Keys and proofs

Nothing on this wire is drawn from `math.random`. CraftOS has no cryptographic
entropy source worth the name, so **every secret and every nonce is derived**,
and uniqueness comes from a durable counter whose increment is committed before
the value is transmitted.

Four labels, each a domain separator so that a value derived for one purpose can
never be replayed as another:

| Label | Derives |
|---|---|
| `craftnet/v1/enrollment\n` | a one-time enrollment secret, from a parent's root secret and a token-use counter |
| `craftnet/v1/relationship\n` | the durable relationship credential, from the enrollment secret and the enrollment transcript |
| `craftnet/v1/session\n` | the session key, from the relationship credential and the session transcript |
| `craftnet/v1/nonce\n` | a nonce, from the relationship credential, a role, and a generation counter |

```
relationship_credential = HMAC-SHA256(enrollment_secret, "craftnet/v1/relationship\n" || CJ1(enrollment_transcript))
session_key             = HMAC-SHA256(relationship_credential, "craftnet/v1/session\n" || CJ1(session_transcript))
```

**Enrollment transcript:** `requested_name`, `role`, `parent_id`,
`relationship_id`, `client_nonce`, `parent_nonce`, `parent_revision`, and
`child_id` only when an existing child re-enrolls after a revocation — so a
first enrollment and a re-enrollment can never derive the same credential.

**Session transcript:** `relationship_id`, `session_id`, `client_nonce`,
`parent_nonce`, `child_revision`, `parent_revision`.

Rules that are easy to violate and expensive to debug:

- **A session ID or nonce is never reused with the same relationship credential.**
- **A reconnect always creates a new session.** An old one is never resumed.
- **A parent invalidates a one-time token only after `enroll_accept` is durably
  committed** — not when it sends it.
- **The generation counter is durable.** A role that bumps it in memory and
  restarts will send a nonce its parent has already seen, be refused as a replay
  — correctly — and sit there unable to reconnect. This was a real defect, found
  by Milestone 8's restart matrix.

A LAN Password is gameplay-grade admission. It gets the offline-dictionary
resistance that implies and no more, which the design accepted deliberately;
what protects it is that a router rate-limits guesses per identity *and* across
the whole LAN.

**Enrollment tokens** are 16 characters of Crockford base32 (no I, L, O, or U,
so nothing reads as something else) carrying 80 bits. The token as typed *is*
the enrollment secret, exactly as a LAN Password is. Deriving rather than
drawing it lets a parent reissue the same token when an Operator loses the
screen, and recognise which token was spent without storing any of them.

Vectors: [`derivation/keys.json`](../../spec/protocol/v1/derivation/keys.json),
[`hash/`](../../spec/protocol/v1/hash/),
[`handshake/`](../../spec/protocol/v1/handshake/).

### Composites

| Type | Fields |
|---|---|
| `source` | `computer_id`, `customer_network_id`, `local_address` |
| `destination` | `customer_network_id`, plus **exactly one** of `computer_id` or `address` |
| `ancestry` | `world_id`, `isp_id`, `customer_network_id`, `router_id`, `computer_id`, `local_address` |
| `address_binding` | `computer_id`, `hostname`, `address` |
| `provider_allocation` | `first`, `last` |
| `error_body` | `code`, `message`, `retryable`, `details?` |
| `traffic_event` | `event_id`, `observed_at_ms`, `world_id`, `direction`, `kind`, `outcome`, `bytes`, and optionally `request_id`, `command_id`, `isp_id`, `customer_network_id`, `router_id`, `computer_id`, `operation` |

**`source` is replaced or verified at every owning hop.** A Customer Router
rebuilds it from the authenticated session rather than believing what the
Computer wrote, which is where "who is asking" stops being a claim.

**A flow ID is paired with the authenticated router relationship.** A bare one
is never globally routable, and that pairing is what makes overlapping RFC 1918
addresses unambiguous: `192.168.1.20` on Home and on Farm are told apart by the
flow, never by the address.

**A Traffic Event is metadata and cannot be anything else.** The field list is
closed, and a field outside it is refused rather than dropped — so a caller that
tries to attach a payload finds out immediately instead of shipping an event
that quietly lost information. There is no `payload`, credential, proof, MAC, or
Access Token field to fill in. Redaction happens at construction, not at
display.

### Naming the External Application

`external_call` is how a Computer reaches `api.craft`. It carries **no
destination**: a `service_request` destination is scoped to a Customer Network
and the External Application is not one, so the kind is the destination. See
[ADR 0010](../adr/0010-name-the-external-application-with-its-own-message-kind.md).

The answer comes back as an ordinary `service_response`, so a reply retraces its
NAT Flow by one rule regardless of what answered it.

**Which credential an operation may present is fixed, and enforced at both
ends** — by the Computer before the call leaves, and by the External Application
on arrival:

| Operation | Presents |
|---|---|
| `device.register` | `registration_nonce` only — the authenticated ancestry *is* the attestation |
| `token.issue`, `device.rotate` | `device_credential` only |
| everything else | `access_token` only |

Any other combination is `invalid_message`. Fixtures assert the wrong ones.

### Configurations

What a role holds, and — separately — what its parent is allowed to hand it.
Each owner wins for the state the authority model assigns to it, so a snapshot
from upstream that tries to rewrite a router's own pool is **not merged and not
obeyed**.

| Role | Complete configuration | A parent may assign |
|---|---|---|
| `computer` | `computer_id`, `hostname`, `address`, `customer_network_id`, `router_address`, `dns_address` | all of it |
| `router` | `customer_network_id`, `customer_network_name`, `router_address`, `dns_address`, `pool_first`, `pool_last`, `lan_operational_channel`, `provider_address`, `isp_id`, `bindings?` | only `customer_network_id`, `customer_network_name`, `isp_id`, `provider_address`, `operational_channel?` |
| `isp` | `isp_id`, `isp_name`, `provider_allocations`, `operational_channel` | all of it |
| `central` | `world_id`, `central_id`, `gateway_url`, `gateway_credential_ref`, `provider_allocations` | all of it |

**A configuration never contains a secret value** — only a reference to one, such
as `gateway_credential_ref`. That is what lets a snapshot be read, relayed,
projected, and shown without anyone having to remember which field was
sensitive.

## The Gateway

One outbound WebSocket per World, opened by the Central Server. Computers,
Customer Routers, and ISPs never open one.

The credential travels in a header, so it never lands in a proxy log or a
browser history:

```
Authorization: Bearer <Gateway Credential>
```

Then the opening exchange:

```json
→ {"v":1,"world_id":"world-overworld","central_id":"central-main",
   "last_topology_revision":31,"last_traffic_sequence":879}

← {"v":1,"gateway_session_id":"gws-000003","accepted_topology_revision":31,
   "accepted_traffic_sequence":879,"server_time":"2026-09-09T12:00:00Z"}
```

Frames afterwards are `{v, kind, request_id?, command_id?, body}`. There is **no
second message HMAC**: the Gateway relies on WSS plus the session it opened.

Rules worth stating outright:

- **A socket is not a session.** Until the welcome decodes there is no Gateway
  Session, and work offered in that window fails `gateway_unavailable`.
- **One live session per World.** A newer connection takes over; the older
  socket is closed rather than left racing it.
- **A browser `Origin` is refused.** The Gateway is not a browser endpoint, and
  a page holding a credential is exactly what must not work.
- **One bad frame is not a reason to lose a World.** A frame that does not
  decode is answered with a stable error, or dropped with its reason recorded —
  the session stays up. Both ends make this claim and both have a test for it.
- **A sequence gap is recorded, never filled.** Traffic Events lost to a
  disconnect are not resent under numbers already spent; the far end records the
  hole rather than showing a plausible present.
- **A replayed older topology is ignored.** Going backwards would make the
  projection lie.

An **Access Token** is an Ed25519 JWT — header `{alg:"EdDSA",typ:"JWT",kid}`,
claims `{iss, aud:"craftnet-gateway", sub, world_id, customer_network_id,
operations, iat, exp, jti}`, with `exp - iat` at most 120 seconds. The External
Application validates signature, issuer, audience, expiry, revocation state,
allowed operation, and **exact ancestry match** — a valid token presented from
another Customer Network is refused. A token it cannot say it issued fails
closed: an unrecognised `jti` is treated as revoked.

**CraftOS treats the token as opaque** and never reads a claim out of it.

Fixtures: [`gateway/frames.json`](../../spec/protocol/v1/gateway/frames.json),
[`tokens/access-token.json`](../../spec/protocol/v1/tokens/access-token.json).

## Limits

CraftNet performs **no fragmentation**. A caller past a limit is told to shrink
its own payload or batch; nothing is split on its behalf.

| Limit | Value |
|---|---|
| Raw-modem frame | 16 KiB after UTF-8 encoding |
| External Operation payload inside one | 8 KiB |
| Gateway message | 256 KiB |
| Traffic Event batch | 100 events and 128 KiB |
| Topology snapshot | 2,000 entities |
| String | 8 KiB unless a narrower rule applies |
| Object depth | 16 |
| Object keys | 128 |
| Array elements | 2,000 |
| In flight per relationship | 64 |
| In flight through the Gateway Session | 256 |
| Access Token life | 120 seconds |

A modem receiver **discards an oversized frame before JSON decoding** — it does
not decode it to find out how big it was.

The two in-flight numbers are different on purpose and live in separate tables.
A World may legitimately have far more outstanding to the External Application
than any one modem relationship may have to its neighbour. Past either bound,
work is refused with `busy`: a queue without a bound is only a slower way of
failing, and it fails later, larger, and somewhere less obvious.

Edges: [`limits/edges.json`](../../spec/protocol/v1/limits/edges.json).

## The error catalog

Every error is `{code, message, retryable, details?}`. `message` is safe to show
a player; `details` carries only non-secret structured context.

**`retryable` describes whether a fresh attempt could succeed. It never
authorizes automatic replay.** CraftNet does not decide on its own to do again
what a player asked for once. The single exception is an idempotent
administrative command resent under the same Command ID.

| Code | Retryable | Meaning |
|---|:---:|---|
| `invalid_message` | no | JSON, type, required-field, or canonical-form validation failed |
| `unsupported_version` | no | Peer does not implement the requested major version |
| `message_too_large` | no | Frame, payload, snapshot, or batch exceeds a limit |
| `busy` | **yes** | Bounded in-flight capacity is exhausted |
| `authentication_failed` | no | Enrollment, session, Gateway, or device proof failed |
| `replay_rejected` | no | Session ID, nonce, request, or counter was reused or out of order |
| `credential_revoked` | no | Durable relationship, device, or Gateway credential is revoked |
| `access_token_expired` | **yes** | The two-minute Access Token is expired |
| `forbidden_operation` | no | Credential is valid but does not authorize the operation |
| `name_not_found` | no | DNS name has no authoritative record |
| `name_conflict` | no | Requested ISP, network, or hostname already exists in its scope |
| `pool_exhausted` | no | No Customer or Provider Address is available |
| `address_conflict` | no | Address is already bound in the relevant scope |
| `router_unavailable` | **yes** | Destination or local Customer Router is disconnected |
| `upstream_unavailable` | **yes** | Immediate parent relationship is unavailable |
| `route_not_found` | no | Central route map has no destination Customer Network |
| `inbound_denied` | no | No matching Exposed Service permits a new remote request |
| `nat_flow_missing` | no | Reply refers to an expired or unknown NAT Flow |
| `network_disabled` | no | Central Network Status disables the Customer Network |
| `gateway_unavailable` | **yes** | Central Server lacks a ready Gateway Session |
| `request_timeout` | **yes** | No terminal response arrived before the operation deadline |
| `revision_conflict` | **yes** | Command or update was based on stale authoritative state |
| `internal_error` | **yes** | An unexpected owner-side failure occurred without exposing internals |

These codes are **wire constants**. They change only by an explicit
wire-version decision — never for implementation convenience. The same
vocabulary is used by the dashboard and the HTTP API, so an Operator sees one
set of words rather than two.

An authentication failure on a discovery channel receives **no detailed
response**, because answering tells a listener on a shared channel something.

Catalog: [`errors/catalog.json`](../../spec/protocol/v1/errors/catalog.json).
What to do about each one, as an Operator:
[Recovery](../operations/recovery.md).

## Changing any of this

A message kind, a field, a limit, or an error code changes only by an explicit
decision recorded as an ADR — not because an implementation found it
inconvenient. The procedure:

1. Decide it, and write the ADR.
2. Change both schemas, Lua and Go.
3. Add fixtures for the new shape **and for what it must now reject**.
4. `make fixtures`, then `make test`. `check-fixtures.sh` proves the catalog
   regenerates to no diff.
5. Update this document.

[ADR 0010](../adr/0010-name-the-external-application-with-its-own-message-kind.md)
is a worked example: it added `external_call` and, with it, a fixture asserting
that an external call naming a destination is refused — so the shape the ADR
rejected cannot be smuggled back in later by a caller.
